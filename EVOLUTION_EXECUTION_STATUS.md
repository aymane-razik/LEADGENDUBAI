# Evolution Plan Execution Status

Updated 1 October 2026. This records implementation after the source review in [the architecture plan](./ARCHITECTURE_REVIEW_AND_EVOLUTION_PLAN.md).

## Delivered in this execution

- Tenant context now runs through `AsyncLocalStorage`; Mongoose models for users, leads, properties, campaigns, activities, and scrapers have a scope plugin that injects the tenant on reads, writes, and aggregation pipelines. Caller-supplied tenant headers are rejected. The current application deliberately admits only the `default` tenant until tenant membership provisioning exists.
- The local Mongo demo database was migrated additively: 240 existing documents received `tenantId: "default"`. Refresh tokens are now stored as SHA-256 hashes. Access and refresh credentials move in HTTP-only cookies; bearer access tokens remain accepted for non-browser API clients. Public self-registration is disabled because it previously allowed privilege selection.
- BullMQ now stores jobs in Redis, with retries, exponential backoff, bounded retention, tenant/correlation metadata, and a separately deployable worker process. Lead enrichment and analytics refresh have real handlers. Campaign dispatch and scraper execution now fail with a visible, actionable reason when their delivery/source adapter is not configured; scraper failures are recorded instead of being reported as successes. The dashboard now calls the route the backend actually exposes.
- NestJS 12.1.1 now owns the API server. The existing Express API is mounted at `/api/v1` as a compatibility adapter. Nest-native endpoints provide liveness/readiness under `/api/v2/health`, lead list/detail/create/status transitions under `/api/v2/leads`, all existing property discovery and CRUD capabilities under `/api/v2/properties`, and activity list/upcoming/overdue/create/read/update/complete/delete under `/api/v2/activities`. These APIs authenticate from the access cookie or bearer token and enforce signed-token tenant context. Leads validate paging/status/ObjectIds and delegate mutations to existing domain services. Properties validate Joi payloads, identifiers, numeric filters, and coordinate bounds. Activities validate payloads, derive the performer from the authenticated identity, and restrict update fields. API and worker lifecycle are separate.
- Drizzle/PostgreSQL 18 schema and migrations are checked in for tenants, users, leads, properties, activities, campaigns, and an outbox. Migrations seed the default tenant and enable tenant row-level security. `withPostgresTenant` sets the transaction-local tenant claim. The application still reads and writes MongoDB; PostgreSQL has not been cut over because this workspace has no configured `DATABASE_URL` or local PostgreSQL service.
- Assignment scoring no longer adds agent performance bonuses to a configured territory/property/timeline mismatch. Auto-assignment now calls the domain assignment engine with persisted agent preferences and actual assigned-lead counts; random load estimates and hard-coded agent IDs were removed. The missing assignment preferences now have a persisted schema with a configurable capacity.
- The production TypeScript build now emits `dist/server.js` as referenced by the package start command. The demo launchers start the BullMQ worker separately from the API.
- The frontend is upgraded to Next.js 16.3.8, with ESLint 9 flat config. The Tailwind 4 animation package is imported from CSS rather than through a missing legacy plugin. Several pre-existing frontend type errors were repaired during the transition.
- The frontend has now been rebuilt around feature-owned screens under `frontend/src/features/*/screens`, with App Router files reduced to route adapters. A Dune midnight visual system replaces the previous generic dashboard: responsive grouped navigation, mobile dock, command palette, funnel and priority panels, editorial login, consistent tokens, and accessible reduced-motion handling. A same-origin Next rewrite proxies `/api/*` to the backend so browser sessions use HttpOnly cookies.
- The account settings screen now persists profile, notification, locale, timezone, and theme preferences through the API. The backend exposes those fields and refuses privilege/email/password changes through that endpoint. Unsafe cookie-authenticated API requests require the configured exact frontend origin; Bearer-token API use remains available for integrations.
- Webhooks now use tenant-scoped persisted subscriptions and delivery attempts instead of process memory. Secrets are encrypted at rest and revealed once at creation. The worker dispatches queued events with HMAC signatures, bounded payloads, HTTPS-only URLs, DNS/IP validation and pinning, and retry metadata. Webhook test/update/delete/history routes are available. Demo webhook examples are inactive and target reserved `.invalid` names.
- The demo recording environment is isolated on API port 5010 and frontend port 3010, with a separate Redis database and the dedicated local Mongo database `dubai-realestate-demo`. `run-demo.bat`, `seed-demo.bat`, and `stop-demo.bat` manage it without killing unrelated Node processes. The deterministic seeder refuses any other database, creates eight users, 60 leads, 35 properties, six campaigns, activities, scraper records, and inactive webhook examples. See [the recording guide](./DEMO_RECORDING_GUIDE.md).
- The public `/` route is now an original anti-marketing landing page with custom SVG Dubai signal-map art, a paper/ink/coral/ultramarine palette, responsive editorial layout, and direct workspace entry. The demo guide includes a recording sequence and all seeded account roles.
- The signed-out session bootstrap no longer tries token refresh or redirects back to `/login` after `/auth/me` returns 401, preventing a page reload/request loop. Expired sessions redirect only from protected pages. Backend Redis rate-limit counters now use separate namespaces for auth, API, and scraping requests.

## Verification

- Backend TypeScript check and production build pass; backend production dependency audit reports zero vulnerabilities. The all-dependencies audit retains four moderate advisories in the Drizzle Kit/esbuild development toolchain.
- Frontend TypeScript check and Next.js 16 production build pass after the redesign. ESLint reports existing warnings but no errors; the project uses async effect-based data loading, so the React synchronous-state-in-effect rule is disabled with an explanation in the flat config.
- The backend suite passed all 14 suites and 80 tests after the leads API migration, and the assignment domain suite passed all 10 tests. The integration assertion checks that an invalid bearer token is rejected with 401 before request-body validation. The subsequently added property and activity Nest modules pass TypeScript checking and the production build; the full suite has not been rerun after those additions.
- Backend ESLint now uses its flat configuration under ESLint 9, but the existing repository-wide lint currently reports 543 errors, mostly existing formatting and unused-import violations. This remains cleanup work; no broad autofix was applied because it would create hundreds of unrelated formatting changes.
- Runtime smoke checks on the dedicated demo stack passed: login returns 200 and HttpOnly cookies, seeded lead/property/activity/webhook lists return the expected records, profile updates persist, and a cross-origin cookie-authenticated profile mutation is blocked. Nest liveness/readiness and the mounted Express `/api/v1/health` route also pass; authenticated lead listing is paginated and a conflicting `x-tenant-id` returns 403.
- The generated PostgreSQL migrations have not been applied to a PostgreSQL instance. No service cutover or Mongo export/import has been attempted.
- Production dependency audits report zero vulnerabilities for both backend and frontend. The full backend dependency tree retains four moderate advisories in the Drizzle Kit/esbuild development toolchain; assess and update that toolchain before release.
